Evaluative breakdown of challenge architecture, infrastructure, content pipeline, and maintenance cost.

Summary

Constraints is a new challenge format where users inherit a working but limited system and must make it survive a real production pressure — verified by an automated test runner, with everything running locally on their machine.

How it differs from existing challenges

Existing CodeCrafters challenges focus on Greenfield implementation, checking protocol specifications. Constraints changes the axis entirely to Brownfield scaling, checking resilience under load.

Existing Challenges
Greenfield builds

You start from nothing and implement a system to spec. The test runner speaks a protocol (Redis/Git) and checks your outputs directly against it.

Constraints Challenges
Brownfield transformations

You start from a working system with a specific weakness. You fix it. The test runner applies real-time traffic pressure and checks overall outcomes — not implementation.

The educational model is identical: no hand-holding, objective pass/fail, and your own tools. The content model is different: instead of a spec to implement, there's a strict physical constraint to survive.

Challenge anatomy

Every Constraints challenge has four modular components designed to slot directly into the existing CodeCrafters ecosystem.

01

The starter repo

A working application, provided as a Git repository. It runs via docker-compose up. It has real code, real dependencies, real behaviour — not a toy. It is deliberately built with a specific weakness that the challenge will expose.

For the Twitter scaling example:

  • Flask app, Postgres database, basic feed/post/follow endpoints.
  • ~500 lines of application code, intentionally naive in specific places.
  • A docker-compose.yml that brings it up in under 30 seconds on any machine with Docker.
02

The stages

Each challenge is broken into 4–6 stages of increasing difficulty. Stages are sequential — you must pass stage N before unlocking stage N+1. Each stage isolates one scaling problem.

  • Stage 1: read path performance
  • Stage 2: write path async
  • Stage 3: fault tolerance
  • Stage 4: stateless services
  • Stage 5: traffic shaping

Each stage has exactly one pass condition. The pass condition is objective and machine-verifiable.

03

The test runner

The test runner is a small Go binary (consistent with CodeCrafters' existing runner architecture) that:

  • Sends HTTP traffic at configurable concurrency and rate.
  • Injects failures (kills containers, introduces latency, drops connections).
  • Measures latency percentiles, error rates, data consistency.
  • Returns pass/fail with a specific, actionable failure reason.

The test runner runs on CodeCrafters' servers. It connects to the user's locally-running system via a temporary tunnel. The runner never needs to execute the user's code — it only speaks HTTP to it.

04

The hints system

Identical to existing challenges. Progressive hints unlocked on demand. No spoilers in the main flow.

Infrastructure model

KEY SECTION

This is the most important section for evaluating overall build cost and computational requirements.

Runs on User's Machine
  • The entire application stack (via Docker Compose)
  • All databases, queues, and caches the user introduces
  • All application code the user writes
Runs on CC Servers
  • The test runner binary (stateless, short-lived)
  • A lightweight tunnel endpoint to reach the local stack
  • The existing challenge platform (unchanged)

The test runner is stateless and short-lived. It spins up, runs a test suite (typically 30–120 seconds of traffic), returns a result, and exits. There is no persistent infrastructure per user. No long-running VMs. No complex Kubernetes clusters.

The tunnel is the only novel infrastructure requirement. This is a solved problem — ngrok, Cloudflare Tunnel, or a self-hosted equivalent. Cost is negligible at CodeCrafters' scale.

Estimated marginal infrastructure cost per challenge attempt: roughly equivalent to existing challenges. The user's machine absorbs the massive compute cost that would otherwise fall on CodeCrafters' servers.

Content pipeline

Writing a challenge

  1. A starter repo — ~1–2 weeks of engineering time to build a realistic but scoped application with deliberate weaknesses.
  2. A test runner configuration — defines traffic patterns, failure injections, and pass conditions per stage. Typically 1–3 days per challenge once the runner framework exists.
  3. Stage descriptions and hints — consistent with existing challenge content effort.

Estimated total effort per challenge: 3–5 weeks for the first few, dropping as the runner framework matures and templates emerge.

Language support

Unlike existing challenges where every language needs a separate starter repo (you implement Redis in Rust vs Go vs Python), Constraints challenges are language-agnostic. The starter repo is the same regardless of what language the user uses to solve it. A user can introduce a Redis cache written in any language they want — the test runner only speaks HTTP.

Leverage
1 challenge = every language

One single starter repo serves all software developers, regardless of their language preference. This provides a significant content leverage point compared to existing paths.

Maintenance burden

Starter repos have real dependencies (Flask, Postgres, etc.) that require occasional updates. This is the primary ongoing maintenance cost. We estimate this to be low. Docker pins versions; the challenge doesn't need to track upstream unless a security issue forces it.

The test runner in detail

Traffic injection

The runner sends HTTP requests using a configurable profile:

  • Concurrency — e.g. 500 simultaneous connections.
  • Request mix — e.g. 80% reads, 20% writes.
  • Duration — e.g. 60 seconds sustained.
  • Ramp profile — e.g. linear ramp from 0 to 500 over 10 seconds.

Failure injection

The runner can execute the following failure modes:

  • Kill a specific Docker container by name (via Docker API or docker kill over SSH).
  • Introduce artificial latency on a specific port (via tc netem on the user's machine — requires a small privileged helper, or approximated by the runner holding connections).
  • Send malformed or adversarial requests.

Pass conditions

Each stage defines one or more measurable outcomes, strictly enforced:

✔ p99_latency_ms < 200 — measured over the traffic window
✔ error_rate < 0.001 — HTTP 5xx rate during failure injection window
✔ data_consistent: true — spot-check reads after writes under concurrency
✔ cross_instance_read: true — upload to instance A, read from instance B

All pass conditions are deterministic given a correct solution. There is no partial credit.

Risk areas

RISK 1 Flakiness

The biggest risk in this format is non-deterministic test results — a correct solution that occasionally fails due to timing, network variance on the user's machine, or Docker overhead.

→ Mitigation: Generous thresholds calibrated against multiple reference implementations on different hardware. Stage pass conditions should be easily achievable on a 4-core laptop, not require a workstation.
RISK 2 Challenge difficulty calibration

Unlike protocol implementation challenges where correct is binary, performance challenges have a continuous output. Setting the right threshold (200ms, not 50ms, not 2000ms) requires testing against multiple naive and correct implementations.

→ Mitigation: Internal testing with a range of solutions before launch. Adjust thresholds dynamically based on cohort data post-launch.
RISK 3 Scope creep in starter repos

A realistic Twitter clone could become very large. The challenge is scoping it to be interesting but completable in a few hours.

→ Mitigation: Strict content guidelines. The starter repo should have exactly the weaknesses the challenge tests — nothing more. Resist realism for its own sake.

Suggested launch scope

One challenge to start. The Twitter scaling example is the right first one — it is well-understood, the stages are clearly separable, and it maps directly onto skills that real engineers recognise from their work.

Launch Spec
  • Five progressive stages
  • One language-agnostic starter repo
  • Go test runner
  • No tunnel complexity at launch (exposing a local port manually)

Validate that the format works, that the test runner is stable, and that users find the difficulty calibration right. Then build the second challenge.

Why this is worth building

System design is the skill gap that determines senior-to-staff promotion more than anything else. No existing platform makes it testable. CodeCrafters' test runner model is the only approach that could make it objective.

The content leverage is unusually high — one challenge works for every language simultaneously. The infrastructure cost is lower than existing challenges because the user's machine does the heavy lifting. And the ROI for users is immediately legible: this is exactly what staff interviews test.

It is the most natural extension of what CodeCrafters already does.
