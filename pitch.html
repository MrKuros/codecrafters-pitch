CodeCrafters: Constraints

The only place to prove architectural judgment — not just describe it.

A hands-on, test-driven curriculum designed to push local implementations to their absolute limits under simulated production pressure.

The problem

System design is the highest-leverage skill gap in engineering right now.

Every existing resource gives you diagrams and explanations. ByteByteGo, Grokking, Hello Interview — they all teach you to recognise good architecture, not produce it. You read about consistent hashing, nod, and move on.

When you're in a real system at 2am, that recognition means nothing.

The insight

CodeCrafters already proved this with Redis and Git.

You don't really understand a system until you've built one. The same principle applies to scaling: you don't understand why Twitter needs a fan-out queue until your naive implementation collapses under a load test.

Constraints applies the CodeCrafters method to the one skill that actually determines whether an engineer gets promoted, passes a staff interview, or earns architectural trust at their company.

How it works

Everything runs locally. Your machine. Your terminal. Your tools. No cloud sandboxes, no custom web IDEs.

Step 01

Clone

Get a working but limited system running instantly on your workstation via Docker.

Step 02

Break it

Step 03

Fix it

Refactor and write real code that survives production-grade constraints, then push to pass.

Example: Scale Twitter

You inherit a working Twitter-like app. Single Flask app, single Postgres instance, a feed endpoint, a follows table. It runs. It just wasn't built for what's about to happen.

The feed is killing the database

Stage 1

The feed query joins across two tables on every request. At 10k users with 500 follows each, it takes 8 seconds. The test runner hits the feed endpoint with 500 concurrent users.

Pass condition: p99 latency under 200ms

The write path can't keep up

Stage 2

Every post synchronously fans out to all followers' feeds. An account with 100k followers blocks the entire app for seconds. The test runner posts from a high-follower account and checks that unrelated users' requests aren't stalled.

Pass condition: regular users see no degradation during a celebrity post

Single point of failure

Stage 3

The test runner kills your Postgres container mid-operation. Read replicas, retry logic, a cache fallback. Fix it however you can so the service remains resilient.

Pass condition: app degrades gracefully (reads may be stale, but must not 500)

The media problem

Stage 4

Images are stored on the local filesystem. The test runner spins up two app instances. An image uploaded to instance A must be readable from instance B.

Pass condition: cross-instance reads succeed via shared object storage

Rate limited by your own users

Stage 5

A bot hammers the API — 500 requests per second from the same IP. Real users are getting 503s. The test runner plays both roles simultaneously to test your ingress limits.

Pass condition: legitimate traffic gets through; bot requests are throttled
